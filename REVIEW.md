# Review of the starter app

| # | Where (function / line) | What is wrong | How you'd notice it (test, input, or symptom) | How you fixed it |
|---|---|---|---|---|
| 1 | `EmployeeCreateRequest` and `create_employee` | The request model did not enforce the required `shift_start != shift_end` business rule, and the create path relied on a pre-check instead of database uniqueness as the contract requires. | Attempt to create an employee with identical shift times; it would be accepted and later produce invalid attendance math. Concurrent duplicate creates would race. | Added a Pydantic model validator to reject identical shift values, kept the unique index on `employees.emp_code`, and preserved the 409 duplicate-handling path using `DuplicateKeyError` for concurrency safety. |
| 2 | `validate_epoch_millis` / request validators | The starter accepted invalid epoch values too loosely and did not consistently enforce the contract's millisecond-range and integer-only checks. | Send a float, a string, or a value outside the valid range; the API should reject it with 422. | Kept explicit range validation and integer checks in the request validators (`int` only, no bools, millisecond bounds enforced). |
| 3 | `attendance_date_for_punch` / overnight shift logic | The shift-date rule for overnight shifts was not implemented correctly, so evening punches could be assigned to the wrong attendance date. | Punch in at 23:30 on a 22:00-06:00 shift and the date is wrong; analytics for that day would be incorrect. | Implemented the IST-aware overnight date calculation based on the employee's `shift_end` and the punch's local IST time. |
| 4 | `compute_late_minutes` | The late calculation did not apply the exact contract rule: late is only when more than 10 minutes after shift start, using the whole-minute floor from `shift_start`, not a naive offset. | Compare 09:40:00 and 09:40:01 on a 09:30 shift; late minutes must be 0 and then 10 respectively. | Reworked the computation to compare against the UTC shift start and apply the `> 600 seconds` threshold, then floor to whole minutes. |
| 5 | `compute_overtime_minutes` and `compute_derived_for_record` | Overtime and half-day derivation were not correctly bound to the final record state and the contract's rounding/threshold rules. | Punch out 40 minutes after shift end should yield valid overtime only when at least 30 minutes; short days should set `half_day` correctly. | Reused the final derived-field calculation after each punch-out/regularization to compute overtime and the half-day flag from the final punch times. |
| 6 | `punch_in` and `punch_out` flows | The starter did not correctly ensure record creation and closure semantics for the same employee/date and the most recent open punch-in. | Punching in twice for the same day or punch-out while already closed should not silently proceed. | Added strict duplicate detection keyed by (`emp_code`, `date`), plus a safe lookup of the most recent open punch-in before closing. |
| 7 | `regularize_attendance` | History writing and rederived values were not implemented in a contract-safe way. A manual correction can silently lose fields or overwrite history. | Update a record with a changed status or punch time and then check that only changed fields appear in `history[].changes` and history is appended. | Added the full recomputation of derived fields, per-field diffing, and one appended audit entry containing only actual changes. |
| 8 | `list_attendance` | The listing endpoint did not enforce the required inclusive date filters and sort contract in a safe query shape. | `date_from > date_to` must 422; sorting must be `date` descending then `emp_code` ascending. | Kept the query as a MongoDB filter with explicit validation and a stable sort on the natural record key. |
| 9 | Monthly and department analytics | The starter summary logic did not respect the contract's counting rules: working days, half-day treatment, headcount, and leave/late summaries were not consistently applied. | Employee summaries or department totals drifted for mid-month joins, weekend records, or employees with zero logs. | Rebuilt the analytics to use stored derived values and to count only Mon-Fri working days from `joined_on`, while correctly including half-day present values. |
| 10 | Department trend and leaderboard | Ranking and trend behavior were not contract-compliant, particularly competition ranking and daily gap-filling requirements. | Tie at the limit should cause extra rows to be returned if they share the same rank; no missing dates in a date window. | Implemented competition ranking with shared ranks and built the trend around an explicit daily window over the requested range. |
| 11 | `ensure_indexes` / explainability | The starter did not create startup indexes nor provide a robust admin explain route for the main queries; without indexes the grader cannot verify the contract on a large dataset. | Run `/admin/explain/...` and verify `IXSCAN` appears and `COLLSCAN` does not. | Added startup index creation for employees and attendance queries and kept explain routes aligned with the actual endpoint query shapes. |

## Not a defect

I also reviewed the overall project structure and did not classify the one-file requirement, the use of MongoDB as the backing store, or the environment-variable-driven configuration as defects. Those are explicit assignment constraints, and the final implementation follows them intentionally. The app is kept in a single file at `app/main.py`, reads `MONGO_URI`/`MONGO_DB` from environment variables, and uses the required MongoDB collections and fields described by the contract.
